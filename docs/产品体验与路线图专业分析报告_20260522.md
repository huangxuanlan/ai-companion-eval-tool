## 1. 执行摘要

长文模式生成工具已经不是一个单一聊天工具，而是一个“Prompt 研发与评估工作台”：它同时承担角色配置、提示词版本管理、单轮/多轮体验、模型横评、Prompt A/B、批量编排、AI 打分、历史复盘、导出归档等任务。

当前最大问题不是功能缺失，而是“工作流对象”没有被产品化。批量测试、模型对比、Prompt A/B、评分、AI 报告、重试、历史记录本质上都围绕同一个实验运行 `Run` 展开，但 UI 仍以页面、弹窗、按钮堆叠为主，导致用户在配置、运行、观察、诊断、修复、复测、沉淀之间频繁跳转，状态容易丢失，心智负担高。

建议的产品北极星：

> 把长文模式生成工具升级为“长文 Prompt 实验工作台”：以 `实验 Run` 为中心串联配置、模型、提示词版本、输入、输出、评分、日志、重试和报告，让每一次验证都可复现、可比较、可诊断、可沉淀。

优先级判断：

- P0：统一“实验 Run”生命周期，修复重试、详情跳转、模型对比状态保留等会直接破坏验证闭环的问题。
- P1：重构信息架构，把对话体验、模型对比、批量测试、A/B、历史复盘纳入统一工作流导航。
- P2：设计系统化，减少视觉噪音、统一图标/状态/按钮/空态/错误态，提升专业工具感。
- P3：把 AI 辅助诊断产品化，包括失败归因、低分聚类、推荐复测集、版本对比结论。

## 3. 大厂产品设计方法论基线

### 3.1 Design Council：双钻模型

Design Council 的 Double Diamond 把设计过程拆为 Discover、Define、Develop、Deliver，并强调发散探索与收敛执行的循环。它也明确提出“以人为先、可视化沟通、协作共创、持续迭代”。参考：[Design Council Framework for Innovation](https://www.designcouncil.org.uk/resources/framework-for-innovation/)。

对本产品的映射：

- Discover：收集真实长文测试失败、低分轮次、模型差异、提示词版本漂移。
- Define：把问题归因到提示词、变量、Few-shot、模型能力、思考配置、评分提示词、运行配置。
- Develop：生成修复方案、A/B 方案、回归样例、复测计划。
- Deliver：跑小规模验证、扩到批量、沉淀版本和报告。

当前产品已经有这些能力，但没有把它们组织成一个显性的双钻工作流。

### 3.2 NN/g：10 条可用性启发式

NN/g 的启发式强调系统状态可见、用户控制、错误预防、一致性、识别优于记忆、效率、极简、错误恢复和帮助文档。参考：[NN/g 10 Usability Heuristics](https://www.nngroup.com/articles/ten-usability-heuristics/)。

对本产品的关键要求：

- 每个 Run 必须让用户知道当前状态：配置是否锁定、正在跑哪批、成功/失败/待重试数量、评分是否完成、报告是否生成。
- 高风险动作必须可恢复或可确认：批量删除、批量重打分、重试、进入完整会话、清空上下文。
- 复杂参数不能依赖用户记忆：模型、提示词版本、thinking、few-shot、评分配置要在结果详情里可见。
- 专家效率要保留：快捷键、模板、批量导入、最近配置、失败项重试。

### 3.3 Google PAIR：AI 产品的人机协同

Google People + AI Guidebook 强调 AI 产品要先确认用户需求与 AI 能力交集，解释 AI 输出，校准信任，提供反馈与控制，优雅处理失败。参考：[PAIR Guidebook Chapters](https://pair.withgoogle.com/guidebook-v2/chapters)、[User Needs + Defining Success](https://pair.withgoogle.com/guidebook-v2/chapters/user-needs/)、[Feedback + Control](https://pair.withgoogle.com/guidebook-v2/chapters/feedback-controls/)、[Explainability + Trust](https://pair.withgoogle.com/guidebook-v2/chapter/explainability-trust/)。

对本产品的关键要求：

- AI 打分必须解释置信度、评分依据、低分归因，而不只是给分。
- 用户必须能修正评分、标记误判、重跑指定项。
- 模型思考开关、思考深度、联网、System Prompt、多样性参数要变成“可解释的控制项”。
- AI 报告应引用证据链：消息快照、请求快照、提示词版本、模型配置、评分提示词版本。

### 3.4 WCAG 2.2：可访问性底线

WCAG 2.2 以可感知、可操作、可理解、健壮为四项基础原则，并提供可测试成功标准。参考：[WCAG 2.2](https://www.w3.org/TR/WCAG22/)。

对本产品的关键要求：

- 键盘行为要一致：Enter 发送、Ctrl+Enter 换行的设计必须在单聊和模型对比都一致。
- 焦点态必须清晰：弹窗、抽屉、下拉、表格行、批量选择要可键盘操作。
- 状态颜色不能只靠颜色表达：成功/失败/运行中/待重试要有文本和图标双编码。
- 复杂表格和结果详情要保持结构化语义。

### 3.5 设计系统参考

本地设计参考资料位于 `E:\提效工具\design-references`，与当前产品最相关的是：

- Linear：暗色优先、低噪边界、精密层级、少量强调色。参考 `E:\提效工具\design-references\linear.app\DESIGN.md`。
- Cursor：开发工具感、编辑器心智、配置与代码内容并重。参考 `E:\提效工具\design-references\cursor\DESIGN.md`。
- Figma：工具型产品的焦点态、工具栏、面板和画布关系。参考 `E:\提效工具\design-references\figma\DESIGN.md`。
- Atlassian：设计 token、内容、可访问性、间距、网格、颜色、字体、图标、边界、圆角等系统化基线。参考：[Atlassian Design Foundations](https://atlassian.design/foundations)。
- Microsoft Fluent 2：跨平台组件、无障碍资源、复杂办公场景的规范化体验。参考：[Fluent 2 Design System](https://fluent2.microsoft.design/)。
- Material 3 与 Apple HIG：可作为组件状态、平台惯例、输入反馈、动效节制的补充参考。参考：[Material Design Foundations](https://m3.material.io/foundations)、[Apple Human Interface Guidelines](https://developer.apple.com/design/human-interface-guidelines)。

结论：本产品应走“Data-Dense Dashboard + Developer Toolbench”路线，而不是营销页或消费级聊天页路线。

## 4. 产品定位与用户分层

### 4.1 产品定位

一句话定位：

> 面向长文 Prompt 研发、模型横评和质量复盘的本地实验工作台。

核心价值：

- 让提示词版本验证从“手工聊天”升级为“可复现实验”。
- 让模型对比从“主观感受”升级为“同输入、同配置、可评分、可导出的证据链”。
- 让失败修复从“凭感觉改 Prompt”升级为“低分归因、指定重试、A/B 验证、历史沉淀”。

### 4.2 用户角色

1. Prompt/人设配置者

目标：维护角色变量、系统模块、Few-shot、提示词版本、摘要/画像/打分提示词。  
关键需求：版本可见、当前生效可见、变量缺失可见、改动可预览、可回滚。

2. 测试执行者

目标：快速跑单聊、批量、模型横评、Prompt A/B。  
关键需求：配置复用、状态清晰、暂停/继续/取消、失败项重试、导出结果。

3. 评估/质检者

目标：查看 AI 打分、人工校准、低分轮次、评分日志、AI 摘要报告。  
关键需求：评分依据透明、失败归因明确、可重打分、可筛选低分、可生成摘要。

4. 运营/复盘者

目标：从历史记录中对比版本、筛选问题、生成复盘报告、沉淀结论。  
关键需求：跨 Run 对比、按模型/提示词/评分维度筛选、导出 Excel/Markdown。

5. 开发/维护者

目标：维护 FastAPI 路由、模型 provider、CLI、测试矩阵。  
关键需求：UI/CLI 规则一致、测试可控、运行时数据不被测试污染、状态对象可追踪。

## 5. 产品路书

这里的“路书”按用户真实任务路径定义，而不是按页面定义。

### 路书 A：单次对话体验路书

目标：快速验证一个角色/Prompt 在真实多轮对话中的表现。

路径：

1. 进入对话体验。
2. 选择主模型。
3. 打开配置面板。
4. 选择角色模板、提示词版本、Few-shot、摘要/画像配置。
5. 设置联网、thinking、自动评分。
6. 输入用户消息并发送。
7. 查看流式输出和轮次进度。
8. 查看调试详情，确认消息拼接和请求快照。
9. 一键打分。
10. 导出 Excel 或保存到历史。

断裂风险：

- 配置面板字段太多，新用户不知道哪些是必填、哪些是高级项。
- 调试详情、评分、导出分散在对话之后，缺少“本轮证据包”概念。
- 输入快捷键曾出现单聊和模型对比不一致的问题，属于基础交互破坏。

建议：

- 将配置面板分为“必选 / 推荐 / 高级”三层。
- 对每轮输出提供“证据包”入口：消息、请求、模型、提示词、评分、日志。
- 单聊与模型对比共享同一输入行为规范。

### 路书 B：模型对比体验路书

目标：同一输入下比较 1-3 个模型的回复质量、风格、稳定性和思考模式影响。

路径：

1. 从对话体验或显性导航进入模型对比。
2. 选择 1-3 个模型。
3. 为每个模型设置 System Prompt、多样性参数、thinking 开关和深度。
4. 输入同一用户消息。
5. 并行生成多模型回复。
6. 点击某个模型回复查看详情。
7. 返回模型对比上下文继续下一轮。
8. 至少 3 轮后生成对比报告。
9. 进入历史记录查看和导出。

断裂风险：

- 模型对比是 `page-freechat`，但主导航不显性，容易被理解成对话页的一个临时模式。
- “查看详情”如果跳转到单模型完整会话，会打断多模型对比上下文。
- 每模型 thinking 控制如果隐藏或状态不清，用户无法知道差异来自模型还是思考配置。

建议：

- 主导航增加“模型对比”一级入口，或在“对话体验”下提供二级 tab。
- 详情默认用侧边抽屉或 modal，不离开对比 Run。
- “进入完整会话”作为显式二级动作，并保留返回原对比 Run 的面包屑。
- 模型列头固定显示模型名、thinking 状态、System Prompt 状态、多样性状态。

### 路书 C：批量测试路书

目标：用 Excel 或当前配置批量跑多轮样本，获得可导出的结果和评分。

路径：

1. 进入测试中心。
2. 选择批量测试。
3. 上传 Excel 或同步当前配置。
4. 设置主模型、并发、run limit、turn limit、dry-run、自动评分。
5. 创建编排 Run。
6. 查看进度、成功、失败、待重试项。
7. 暂停、继续、停止或重试失败项。
8. 导出结果和摘要。
9. 进入历史复盘。

断裂风险：

- “重试失败项”如果没有绑定原 Run 的失败集合，容易变成完全重跑。
- 配置快照不够显性，用户难以确认这批结果用的是哪版 Prompt、哪组模型、哪组评分提示词。
- 批量进度、评分进度、摘要进度可能分属不同状态，用户会混淆。

建议：

- 定义 Run 状态机：Draft → Queued → Running → Partially Failed → Scoring → Report Ready → Archived。
- 重试必须显示重试范围：失败 N、未完成 M、跳过已成功 K。
- 每个 Run 固化配置快照，不允许结果页只显示“当前配置”。

### 路书 D：Prompt A/B 实验路书

目标：对比控制组和实验组提示词或模型，判断改动是否提升质量。

路径：

1. 进入测试中心。
2. 选择 Prompt A/B。
3. 选择控制组 Prompt/模型。
4. 选择实验组 Prompt/模型。
5. 选择输入样本或 Excel。
6. 设置评分模型、评分提示词、维度权重。
7. 运行实验。
8. 对比通过率、均分、低分维度、典型轮次。
9. 生成实验结论。
10. 将胜出版本设为候选或生效版本。

断裂风险：

- A/B 与提示词管理割裂，实验胜出后缺少“设为候选版本”的产品闭环。
- 报告如果只展示平均分，不展示样本级证据，容易误判。
- 控制组/实验组配置差异可能不止 Prompt，需防止变量或模型配置污染结论。

建议：

- A/B 报告必须显示差异清单：模型、主提示词、摘要提示词、打分提示词、Few-shot、变量。
- 给出“可信结论 / 需复测 / 样本不足”的结论等级。
- 从报告直接发起“扩大样本复测”。

### 路书 E：提示词版本管理路书

目标：维护主提示词、摘要提示词、打分提示词、画像提示词的版本生命周期。

路径：

1. 进入提示词管理。
2. 选择提示词类型。
3. 查看当前 active、latest、历史版本。
4. 上传或新建版本。
5. 预览差异。
6. 运行 smoke 或指定黄金用例。
7. 设为生效版本。
8. 记录版本说明。

断裂风险：

- active/latest 语义必须清晰，否则目录重组或归档目录会影响用户对“最新”的信任。
- 编辑与验证割裂，提示词保存后未必能立即发起对应回归。
- 归档版本不能参与自动 latest，但必须可查。

建议：

- 管理页显示 `active`、`latest`、`archived` 三种状态。
- 每次版本变更提供“运行黄金测试”入口。
- 版本详情展示被哪些 Run 使用过。

### 路书 F：历史复盘路书

目标：从历史中找问题、生成报告、沉淀结论。

路径：

1. 进入历史记录。
2. 按模型、Prompt 版本、评分状态、时间、低分维度筛选。
3. 打开某个 Run 或会话详情。
4. 查看消息、评分、AI 摘要、事件日志。
5. 批量导出、批量重打分或生成对比报告。
6. 将结论沉淀到文档或下一轮实验。

断裂风险：

- 历史页操作太密：批量删除、批量重打分、批量摘要、对比、归档、日志导出都在同一区域。
- 用户需要区分“会话历史”和“实验 Run 历史”，当前心智可能混杂。
- 高风险操作需要更强选择态和结果反馈。

建议：

- 历史分为“实验 Run”和“单会话”两个视图。
- 批量操作统一进入确认抽屉：范围、影响、是否可恢复。
- 每个历史项显示来源：单聊、模型对比、批量测试、A/B。

### 路书 G：失败诊断与复测路书

目标：从失败或低分结果出发，定位根因并验证修复。

路径：

1. 从批量结果或历史记录进入失败/低分项。
2. 查看失败类型：接口失败、超时、评分失败、低质量、变量缺失、Few-shot 不匹配、模型不支持 thinking。
3. 查看证据：请求、响应、提示词、模型配置、评分理由、日志。
4. 选择修复方式：重试、改配置、改 Prompt、换模型、调整 scoring prompt。
5. 自动生成复测集。
6. 跑复测。
7. 对比修复前后结果。

断裂风险：

- 失败项如果只显示错误文本，用户无法知道下一步该做什么。
- 重试、重打分、重新生成、重新摘要是不同动作，必须清楚区分。

建议：

- 失败详情页采用“诊断卡”：问题类型、影响范围、推荐动作、证据链接。
- 重试按钮命名精确：重试生成、重试打分、重试摘要、重试失败项。

## 7. 体验断裂点分析

### P0-1：缺少统一实验 Run 对象

现象：

- 批量测试、模型对比、Prompt A/B、评分、报告、历史记录都像独立功能。
- 用户完成一次验证后，难以从一个地方看到配置、输入、输出、评分、日志、重试、报告。

影响：

- 难以复现结果。
- 重试和重打分的范围容易误解。
- 历史复盘成本高。

建议：

- 建立产品层 `Run` 概念，不一定立刻大改数据库，先从 UI 和 API 响应聚合开始。
- Run 详情页包含：配置快照、输入样本、模型列表、提示词版本、状态流、结果、评分、报告、日志、操作历史。

### P0-2：模型对比详情跳转破坏上下文

现象：

- 用户在模型对比中点击某个回复详情，会进入该模型的具体会话。
- 返回首页对话体验后，对比状态可能重置。

影响：

- 用户正在做横评时被强制切到单模型纵向会话。
- 继续测试需要重新选择模型和配置。

建议：

- 默认用详情抽屉或 modal 展示，不离开模型对比页。
- “进入完整会话”保留，但必须是显式二级动作。
- 完整会话页顶部保留返回原 Run 的面包屑。
- 模型对比状态持久化到 session/run，而不是纯前端临时状态。

### P0-3：失败项重试语义不清

现象：

- 用户反馈“批量测试终端重试失败项，怎么完全重跑了”。
- UI 存在“重试失败/未完成项”入口，但如果后端或前端没有把失败集合绑定到原 Run，就会产生完全重跑感知。

影响：

- 浪费成本。
- 覆盖或混淆已成功结果。
- 用户不再信任批量执行状态。

建议：

- 重试前显示范围预览：失败项 N、未完成项 M、已成功跳过 K。
- 重试 Run 必须引用 parent run id 和 item ids。
- 结果页区分“原始成功”“本次重试成功”“本次重试失败”。

### P1-1：信息架构以页面为中心，而不是以任务为中心

现象：

- 主导航四项过粗，但实际功能很多。
- 模型对比作为隐藏 `page-freechat` 存在，不是稳定入口。
- 测试中心内同时承载批量、模型对比、A/B、Excel 配置和编排状态。

影响：

- 新用户不知道从哪里开始。
- 老用户依赖记忆找功能。
- 功能越多越难维护。

建议：

将主导航调整为：

1. 工作台
2. 实验
3. 模型对比
4. 提示词
5. 历史
6. 设置

或采用二级 IA：

- 验证：单聊、模型对比、批量测试、A/B
- 资产：提示词、变量、Few-shot、模板
- 复盘：历史、评分、报告、导出
- 设置：模型、Provider、路径、运行参数

### P1-2：配置面板过载

现象：

- 右侧配置面板同时管理角色变量、系统模块、Few-shot、画像、摘要、模型、提示词版本、采样参数、模板保存。

影响：

- 新用户难以判断哪些字段会影响当前运行。
- 高级参数挤压核心参数。
- 配置错误在运行后才暴露。

建议：

- 分层：基础运行、Prompt 资产、模型与思考、评分与报告、高级调试。
- 增加运行前检查：必填缺失、版本不存在、模型不支持 thinking、Few-shot 路径为空、评分提示词缺失。
- 运行后锁定配置快照，避免“当前配置”和“历史结果”混淆。

### P1-3：思考模式控制缺少统一能力模型

现象：

- 单聊、模型对比、评分链路都涉及 thinking，但不同模型支持情况不同。
- 用户需要知道“这个模型能否开思考”“能开哪些深度”“关闭时会怎样”。

影响：

- 用户误以为所有模型都支持相同 thinking effort。
- 结果差异无法解释。

建议：

- 建立模型能力矩阵：`supports_thinking`、`thinking_efforts`、`default_effort`、`provider_mapping`、`unsupported_reason`。
- UI 用每模型列头控制，而不是只用全局 thinking。
- 不支持时禁用控件并展示原因。
- 报告中记录每轮实际发送的 thinking 配置。

### P1-4：评分链路状态不可解释

现象：

- 存在 AI 打分、重打分、失败重试、AI 摘要、低分导航、评分事件日志等功能。
- 这些能力说明评分链路已经复杂，但用户看到的可能仍是按钮和弹窗。

影响：

- 用户难以判断评分失败是模型失败、提示词失败、格式失败还是网络失败。
- 低分修复动作不明确。

建议：

- 评分详情拆为：评分状态、维度得分、理由、证据、错误、重试历史。
- 增加低分聚类：剧情推进、角色一致性、情绪递进、上下文记忆、表达自然度等。
- AI 摘要报告必须绑定评分版本和评分提示词版本。

### P2-1：视觉语言不够统一

现象：

- 页面中存在 emoji 图标、手写 SVG、文本按钮混用。
- 弹窗、抽屉、按钮、表单、状态条的层级不完全统一。

影响：

- 工具专业感下降。
- 操作优先级不清晰。

建议：

- 统一图标库，按钮采用图标 + tooltip 或明确文本。
- 采用 Data-Dense Dashboard 风格：高密度但低噪，减少装饰性元素。
- 保留 8px 以内圆角，区分主操作、次操作、危险操作。
- 表格/结果页优先密度、对齐、筛选、状态，而不是卡片堆叠。

### P2-2：Web 与 CLI 心智未统一

现象：

- Web 是完整工作台，CLI 是 `longform_multi_turn.py` 主链路。
- 架构文档记录 CLI 与服务层存在常量副本债务。

影响：

- 同一配置在 Web 和 CLI 可能表现不一致。
- 用户无法确认 CLI 结果能否回到 Web 历史中复盘。

建议：

- 定义统一配置 schema。
- CLI 输出 Run manifest，可被 Web 导入。
- Web 导出的配置可被 CLI 直接运行。

## 9. UI 设计系统建议

### 9.1 视觉方向

推荐风格：Data-Dense Dashboard + Developer Toolbench。

设计原则：

- 以内容和状态为中心，减少装饰。
- 深色或中性浅色都可以，但必须有稳定 token。
- 主要强调色只用于主操作、选中态、关键状态。
- 复杂配置优先表单密度和分组，不使用大卡片堆叠。
- 结果页优先表格、筛选、固定列、批量操作。

### 9.2 核心组件

- Run 状态条：Queued / Running / Scoring / Failed / Partial / Report Ready / Archived。
- 模型能力徽标：Thinking、Web、Vision、JSON、Streaming、Tool。
- 配置快照面板：只读，支持复制和导出。
- 结果表格：状态、模型、轮次、分数、错误、重试、详情。
- 诊断抽屉：证据、错误、推荐动作。
- 对比矩阵：模型 × 轮次 × 评分维度。
- 版本 Diff：Prompt 版本差异和影响范围。

### 9.3 交互规则

- Enter 发送，Ctrl+Enter 换行；单聊、模型对比、Prompt 测试输入一致。
- 点击模型回复详情默认不跳页，只打开抽屉。
- 离开运行中页面前提示状态保留方式。
- 高风险操作统一确认：删除、清空、批量重打分、完全重跑。
- 所有批量动作先预览范围。
- 所有 AI 结论必须能展开证据。

## 10. 路线图

### 近期：0-2 周

目标：修复最破坏信任的体验断裂。

任务：

1. 模型对比详情改为 modal/drawer，不默认跳转完整会话。
2. 模型对比状态持久化，返回首页不丢失当前对比上下文。
3. 单聊和模型对比统一 Enter/Ctrl+Enter 输入行为。
4. 每模型列头显示独立 thinking 控制和实际支持状态。
5. 批量重试失败项增加范围预览，只重试失败/未完成 item。
6. Run/结果详情显示配置快照：模型、Prompt、Few-shot、thinking、评分提示词。
7. 提示词 latest/active/archived 状态在管理页显性展示。

验收标准：

- 从模型对比打开详情再返回，不丢失 3 个模型、历史轮次和输入草稿。
- 重试失败项不会重新跑已成功项，UI 显示跳过数量。
- 单聊和模型对比键盘行为一致。
- 不支持 thinking 的模型控件禁用且展示原因。

### 中期：1-2 个月

目标：把功能堆叠升级为实验工作流。

任务：

1. 引入 Run 详情页，把批量、模型对比、A/B、评分、报告聚合。
2. 重构测试中心为“验证”二级导航：单聊、模型对比、批量、A/B。
3. 历史记录拆为 Run 历史和会话历史。
4. 建立模型能力矩阵配置和前端渲染协议。
5. 建立统一配置 schema，Web/CLI 共用。
6. 提示词版本详情增加“被哪些 Run 使用过”。
7. AI 报告生成结构化摘要：整体表现、优势、不足、建议、Top 轮次、维度洞察。

验收标准：

- 任意结果可回到完整 Run 详情。
- 任意 Run 可导出 manifest 并复现。
- CLI 输出可导入 Web 历史或至少可在 Web 中查看报告。
- A/B 报告能列出控制组/实验组全部差异项。

### 长期：3-6 个月

目标：从验证工具升级为 Prompt 研发平台。

任务：

1. 失败诊断引擎：接口失败、格式失败、低质失败、变量缺失、Few-shot 不匹配等自动归因。
2. 低分聚类和修复建议：按评分维度生成复测建议。
3. 自动黄金测试集：从历史低分和高价值样本沉淀 regression set。
4. 成本/速度/质量三维模型选型报告。
5. Prompt 版本准入流程：编辑 → smoke → 小批量 → A/B → 候选 → active。
6. 多用户/团队协作准备：Run 注释、报告分享、变更记录。

验收标准：

- 每次 Prompt 变更都有最低验证门槛。
- 历史低分可以自动转为复测集。
- 模型选型报告能解释质量、成本、速度和失败率。

## 11. 验收指标

### 产品指标

- 首次成功跑通单聊时间：目标 < 3 分钟。
- 从批量失败到成功重试的操作步数：目标 <= 3 步。
- 模型对比详情返回后状态保留率：目标 100%。
- Run 可复现率：目标 100% 记录配置快照。
- 报告可直接复盘率：目标每份报告包含配置、结果、评分、结论、证据。

- 用户无需记忆即可识别当前模型、Prompt 版本、thinking 状态。
- 所有批量动作都有范围预览。
- 所有运行中任务都有状态、进度、取消/暂停策略。
- 所有错误都有下一步建议。

### 工程指标

- UI/CLI 共享配置 schema。
- 前端按领域拆分，降低 `legacy_bundle.js` 单文件复杂度。
- 测试分层清晰：unit / integration / smoke / regression。
- 测试不触碰运行时真实数据库。
