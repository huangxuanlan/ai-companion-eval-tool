# 长文模式生成工具 PRD v0.1 结构化初稿

## 摘要
本次不是新做一个“短文工具”或“提示词平台”，而是基于现有长文模式生成工具做一次产品级升级，把它从“长文验证工具”升级为“提示词测试工具”，但仍沿用现有工具骨架、页面命名和使用习惯。

v0.1 的产品骨架固定为三块：
- `对话体验`：即时试针工作区，负责单条验证、实时聊天、快速横看
- `测试中心`：正式测试任务编排器，负责批量测试、Prompt A-B、模型对比、综合对比
- `历史记录`：证据沉淀区，负责回看、追溯、复盘、复用

前端一级文案继续沿用现有体系，不新增“试针台”“实验场”之类新黑话。提示词管理不再单独做成一级导航实体，而是融入 `对话体验 > 参数 > 提示词配置` 与 `测试中心` 的正式测试流中，避免工具继续肿胀。

## 产品定义
### 1.1 产品定位
长文模式生成工具升级版，是一个面向提示词迭代、模型选择、消息拼接验证的统一工具。
它服务的不是“只测长文”，而是“验证一条提示词方案在不同消息拼接模式下的真实表现”。

### 1.2 核心问题
- 现有工具强绑定长文模式，导致短文模式、混合路径、切换路径无法在同一套验证链路中比较。
- 现有实时聊天、批量测试、历史追溯之间割裂，试出来的结果难以沉淀成正式证据。
- 提示词版本、模型参数、消息拼接方式没有被当成同级变量管理，导致后续 Prompt A/B 或模型对比无法稳定复现。
- 如果继续给“长文工具”硬塞一个“短文模式”，会让用户感知成臃肿叠加，而不是能力升级。

### 1.3 设计原则
- 升级，不推翻：保留现有长文工具导航、语言体系和主要交互骨架。
- 一套壳，两类能力：前台仍是一套工具，底层支持不同消息拼接模式。
- 先即时验证，再正式测试：对话体验负责快速判断，测试中心负责可复现结论。
- 模式是一级变量：`mode` 必须显式可选，不能藏在参数深处。
- 不额外造“提示词管理中心”：版本管理依附试验和测试，而不是独立做一个 CMS。
- 结论先行，证据紧跟：所有综合比较都先给推荐方案，再给证据拆解。

## 信息架构与关键接口
### 2.1 一级导航
- `对话体验`
- `测试中心`
- `历史记录`

### 2.2 模式体系
v0.1 固定支持四类模式：
- `longform`
- `shortform`
- `switch_short_to_long`
- `switch_long_to_short`

实现上不要求前端暴露“技术名”，但后端、运行记录、测试记录必须显式保存该字段。

### 2.3 核心抽象
系统统一围绕 4 个对象工作：
- `提示词版本`：一份可被选择、编辑、存草稿、发布的提示词资产
- `模式`：决定消息拼接方式、运行时上下文策略、可比性边界
- `运行记录`：一次对话体验或一次测试分支的真实执行结果
- `来源链路`：一条记录从哪里来、基于哪个样本、哪个模式、哪个模型、哪个提示词版本生成

### 2.4 需要显式新增或补齐的接口字段
- `mode`: `longform | shortform | switch_short_to_long | switch_long_to_short`
- `entry_surface`: `chat | test_center | history_replay`
- `prompt_version_id`
- `prompt_version_status`: `draft | published`
- `request_assembly_strategy`: 标识真实消息拼接策略
- `source_group_id`: 多模型聊天或综合对比的一组关联记录 ID
- `source_parent_id`: 从哪条记录衍生
- `sample_source_type`: `history_sample | file_import | manual_input`
- `hard_failure_status`: 是否命中硬错误
- `weight_profile_id`: 综合对比时采用的权重配置

这些字段不是为了做复杂建模，而是为了让一次结论可以被复现、追责和复盘。

## 页面设计
### 3.1 对话体验
定位：即时验证主工作区，解决“这版提示词现在到底行不行”。

顶部一级控件固定为：
- `模式`
- `模型`
- `提示词版本`
- `模型对比`

右侧结构继续沿用现有双 Tab：
- `角色`
- `参数`

`参数` Tab 保持三段：
- `模型配置`
- `提示词配置`
- `运行参数`

`提示词配置` 默认交互定稿为：
- 一个版本下拉
- 一个 `编辑` 按钮
- 一个 `存草稿` 按钮
- 一个 `发布` 按钮
- 发布前必须满足：至少 1 次对话体验验证记录 + 至少 1 次测试中心正式测试记录
- 已发布版本默认只读；点击 `编辑` 后进入草稿态，不直接覆盖已发布版本
- 版本切换时若有未保存改动，弹确认，不静默丢失

对话体验一期能力固定为：
- 单模型实时聊天
- 多模型聊天
- 重新生成
- 自动打分开关
- 消息详情
- 查看完整请求
- 清空会话
- 关闭抽屉或退出当前体验容器

这里的“抽屉”不单独定义成新产品实体，只视为对话体验的一种承载形态；能力与主工作区共用一套逻辑，不做第二套信息架构。

AI 消息卡片底部一级操作固定为：
- `查看依据`
- `消息详情`
- `查看完整请求`
- `重新生成`

多模型聊天的产品定位固定为：
- 只做快速横看
- 不承担正式报告主出口
- 一组会话产生多条子记录，并写入同一 `source_group_id`

短文模式接入原则：
- 不新增单独页面
- 在同一个 `对话体验` 中通过 `模式` 切换
- 仅替换消息拼接策略、运行时上下文和详情展示内容
- UI 文案尽量沿用现有长文页面表述，不创造新术语

### 3.2 测试中心
定位：正式测试任务编排器，解决“这版方案在一批真实样本上到底更不更优”。

首页编排顺序固定为：
- `模式 / 任务类型`
- `样本来源`
- `提示词版本 / 模型`
- `评分与运行参数`

任务类型固定为：
- `批量测试`
- `Prompt A-B`
- `模型对比`
- `综合对比`

样本来源固定为双入口：
- `历史样本`
- `文件导入`

设计约束：
- `Prompt A-B`、`模型对比`、`批量测试` 是同一编排体系内的不同任务类型，不再拆成互相孤立的工具页
- 允许长文、短文、混合模式都进入测试中心
- 不假设跨模式天然同构；综合对比比较的是“整体产品路径表现”，不是单轮文本长短谁更好

综合对比报告首页顺序固定为：
- `当前推荐方案`
- `路径总分`
- `硬失败状态`
- `权重拆解`
- `关键失败样本`
- `下钻入口`

权重拆解首页默认展示：
- 当前生效权重方案名
- 三条路径权重
- 各路径得分
- 最终加权结果

硬错误策略固定为：
- 一票降级
- 总榜可以展示，但必须显式标红硬失败，不允许漂亮总分掩盖硬错误

### 3.3 历史记录
定位：统一证据沉淀区，不只是“聊天存档”。

二级结构固定为：
- `对话记录`
- `测试记录`

历史页展示原则：
- 历史记录为主
- 版本信息为辅
- 不做复杂树状结构
- 用 `来源链路卡片` 呈现记录关系

来源链路卡片字段顺序固定为：
- 来源类型
- 模式
- 模型
- 提示词版本
- 样本来源
- 创建时间
- 来源父记录
- 关联分组记录数
- 进入详情入口

多模型聊天留痕方式固定为：
- 一组会话，多条子记录
- 历史页按组聚合展示，详情页按子记录展开

## 评分、报告与验收
### 4.1 评分与裁决
评分体系采用分层裁决：
- 单轮评分看文本质量与规则符合度
- 路径评分看整条体验链路
- 综合结论先看硬错误，再看加权总分

### 4.2 v0.1 默认验收场景
- 单模型长文对话能正常试跑、打分、看消息详情、看完整请求
- 单模型短文对话能正常试跑，且消息详情展示的是短文真实拼接结果
- 多模型聊天能在同一轮输入下并排展示多模型输出，并以一组会话沉淀到历史记录
- 测试中心能对长文与短文分别做批量测试
- Prompt A-B 能在同一模式下比较两个提示词版本，不把短文和长文错误混成同一种对比
- 模型对比能在同一模式、同一数据集下输出正式报告
- 综合对比能比较不同模式路径，并展示权重拆解与硬失败状态
- 历史记录能从一条结果追到其来源链路，看到它来自哪次试聊、哪次正式测试、哪个版本
- 已发布提示词不能被直接改脏；必须经草稿态修改并重新发布
- 发布前门槛有效，不能跳过试聊证据和正式测试证据

### 4.3 本版明确不做
- 不新开一级导航 `提示词管理`
- 不做独立“长文工具”和“短文工具”双产品
- 不做复杂流程树、血缘图谱或多层实验空间
- 不在对话体验里生成正式综合报告
- 不把跨模式结果强行放进一个天然可比的单榜里

## 默认实现假设
- 落盘文件名默认使用 `长文模式生成工具_PRD_v0.1_20260424.md`
- 提示词版本继续基于现有本地版本资产与现有后端版本机制，不在 v0.1 引入新的提示词数据库
- 综合对比的具体权重数值不在 v0.1 文档中写死，由配置给出；UI 必须展示当前生效权重
- 若现有前端已有抽屉交互，则对话体验复用抽屉外壳；若没有，则以现有页面容器实现，不额外造第二套入口
- 现有长文模式前端文案优先复用，例如 `对话体验 / 测试中心 / 历史记录 / 自动打分 / 消息详情 / 查看完整请求`

## 外部参考
这版结构吸收了几类成熟产品的共性做法，但没有直接照搬它们的名词体系：
- GitHub Models：把 `Playground`、`Comparisons`、`Prompt Configurations` 分成不同职责层，强调“快速试验”和“结构化比较”分离  
  https://docs.github.com/en/github-models/about-github-models  
  https://docs.github.com/en/github-models/use-github-models/evaluating-ai-models
- Langfuse：把 `Datasets`、`Experiments`、`Versions` 拆开，强调数据集版本和实验复现  
  https://langfuse.com/docs/experimentation  
  https://langfuse.com/docs/evaluation/experiments/experiments-via-ui
- Promptfoo：强调数据集是 eval 的核心，批量测试应围绕真实输入组织  
  https://www.promptfoo.dev/docs/intro/  
  https://www.promptfoo.dev/docs/configuration/datasets/
- OpenAI Evals：强调评测应持续积累、持续复跑，而不是一次性人工判断  
  https://platform.openai.com/docs/guides/evaluation-getting-started  
  https://platform.openai.com/docs/guides/evaluation-best-practices
